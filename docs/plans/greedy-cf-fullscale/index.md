## Context

The `/plan-post-review` of the completed `iterative-greedy-cf` plan (2026-07-07) rated the implementation **"Minor issues"**: the greedy mechanism, both selectors, kNN context, routing override, and discrete dataset are correct and well-tested, and the guardrails hold perfectly (zero `src/tabpfn/**` edits, zero `tabpfn_client` imports). The findings that remain:

**P1 — Exp7 saturation shortcut is unsound.** `exp7_budget_sweep.py:308` copies larger-budget rows when `metrics["steps_max"] < budgets[next_idx]`. Two defects: (1) `steps_max` (`exp4_greedy_cf.py:296`) is computed over **valid/flipped CFs only** — budget-bound *failures*, exactly the points a larger budget could rescue, are excluded from the "can a bigger budget bind?" test; (2) it compares against `next_budget`, not `current_budget`. On HELOC the shortcut fired at budget 17, so rows for budgets 34/51/100/250/1000 are **copied, not measured** → the "validity plateaus at 0.8 across all budgets" conclusion (the central Stage-5 deliverable) is under-evidenced. Concrete proof the copy is lossy: in `exp7_budget_moons.csv`, `lof_scores_cf` differs between budget 2 (1.0267) and budget ≥4 (1.0075), proving a point *was* cut off at budget 2.

**P2 — `exp7_budget_moons.csv` is inconsistent with the committed code.** All 6 MOONS rows have distinct non-zero `runtime_s` (shortcut never fired), but the current code *would* fire it at budget 2 and copy 5 zero-runtime rows. The MOONS artifact was produced by a pre-shortcut code state → not reproducible; the two Exp7 CSVs were generated by different code states.

**P2 — Stage-3 byte-identical regression guard is vacuous.** `tests/test_context.py:36` (case a) builds `rng.choice(...)` twice inline and asserts they are equal — it never calls `set_context`, so it always passes regardless of sampler behaviour. The plan's single most important regression guard is effectively absent (the underlying code *is* byte-identical today, so no live bug — but a future reseed/refactor would drift silently).

**P3s** — `class_divergence` stall guard misses 2-feature oscillation (`greedy.py:212`); `exp6_context_ablation.write_summary()` emits a placeholder verdict that would clobber the hand-finalized `exp6_summary.md` on re-run; the predecessor index cites Stage-1 commit as `5dfcaba` (that hash lives on the successor `manifold-flow-cf` branch — the actual commit on `iterative-greedy-cf` is `d1a5352`), and several tracker rows say "(see git log)"; the `binary_cat` discrete sanity check sets label `Y = decision_code = actionable feature 0`, so `validity=1.0` is partly circular and only weakly stresses the classifier head.

**Statistical-noise debt (the review's cross-cutting gap).** Per predecessor Decision #13, HELOC experiments were bounded to `--max-test 15` (Exp6) / `50` (Exp5) / `30` (Exp7). At n=15 the validity granularity is ±0.12, so the predecessor's own reports lean on the monotone `frac_oob`/`LOF` trends and treat validity as noisy. To publish, the headline configs need tighter CIs. **Decision (2026-07-07, user): re-run at statistically-stable bounded sizes — HELOC n≈200, MOONS full (~200 test rows)** — not the entire 2092-row HELOC split (the 16-cell kNN grid would take weeks; see Decision #4 below).

**Backlog #4 (predecessor) — full-size Exp9 never finished.** The forced-numeric routing override exhausts the greedy budget, hitting `prob_ascent`'s O(|A|²) candidate-scan worst case with per-query kNN fits; only an n=1 smoke is committed. This plan makes it tractable with a reusable candidate-caching + beam-cap speedup and runs it at scale.

Baselines to beat/reproduce (predecessor headline, memory `iterative-greedy-cf-results`): greedy `prob_ascent` lifts HELOC validity 0.538→**0.90** (n=50), L0 17→**1.67 distinct**, proximity 1.69→**0.63**; `knn_both@256` gives frac_oob 0.653→**0.0**, LOF 5.68e9→**1.98**. MOONS plateaus **0.70–0.82** with ~30% failure_rate (the deterministic near-MAP plateau — only 2 actionable features). These n=15–50 numbers are what the full-scale runs must confirm at tighter CIs.

## Strategy

Three phases. **Phase A** must land before Phase B (the experiments depend on the corrected sweep logic, the programmatic summary writer, and the speedup). Phase C consolidates.

- **Phase A — Fixes & speedup (local, fast, no GPU required for the code; tests via `uv`)**:
  - **Stage 1 — Exp7 shortcut fix (P1)**: correct the saturation-shortcut predicate (gate on max steps over *all* points vs *current* budget, or drop the shortcut); add a unit test that pins when it may fire.
  - **Stage 2 — Test & doc hardening (P2 + P3s)**: make `test_context.py` case-(a) actually exercise `set_context(selection="random")` and pin indices; make `exp6_context_ablation.write_summary()` derive its verdict programmatically; fix the predecessor index Stage-1 SHA + backfill "(see git log)" rows; add the `binary_cat` circular-label caveat to `REPORT.md`.
  - **Stage 3 — Greedy speedup: candidate caching + beam cap**: within-step memoization of `sample_feature`/score per `(row, col)` and an optional `--beam K` candidate cap threaded through exp4/exp6/exp7/exp9; default behaviour byte-identical (no beam ⇒ exhaustive scan; caching transparent). Also strengthen/document the `class_divergence` stall guard (P3). Unblocks Exp9 at scale and speeds every greedy run.
- **Phase B — Full-scale experiments (heavy, run on the remote DGX `gx10-bdc5` per predecessor Decision #12; HELOC n≈200, MOONS full)**:
  - **Stage 4 — Exp5 selector ablation** at full scale.
  - **Stage 5 — Exp6 context ablation** (16-cell grid) at full scale — the dominant-cost stage (~3 DGX-days).
  - **Stage 6 — Exp7 budget sweep** with the fixed shortcut — regenerates *both* CSVs from one code state (closes P2 reproducibility).
  - **Stage 7 — Exp9 routing override** at n≥30 (target n=200 if the Stage-3 speedup makes it tractable) — resolves predecessor Backlog #4.
- **Phase C — Consolidation (local)**:
  - **Stage 8 — Full test suite + consolidated table + REPORT + memory**: run the *entire* pytest suite (not the bounded per-stage subsets), rebuild `summary_table.{md,csv}` and `REPORT.md` from the new full-scale CSVs, update the two NeoCortex memories, and flip predecessor Backlog #4 → RESOLVED.

Dependencies: Stage 1 → Stage 6; Stage 2 (`write_summary`) → Stage 5; Stage 3 → Stage 7 (and speeds 4–6); Stages 4–7 → Stage 8. Stages 1/2/3 are mutually independent. All Phase-B stages require the host preflight in `resources/commands.md` to pass first.

## Execution Protocol

This plan is built for **autonomous, unattended execution**. The guiding principle is
**keep making progress**: resolve problems in place when you can, defer them when you
can't, and never halt the whole plan over a single fixable or deferrable issue.

### Required host preflight (blocks Phase B)

Before starting any Phase-B stage (4–7), run the **Host preflight** in
`resources/commands.md` on the DGX execution host. This is a hard prerequisite because
the repo intentionally does not track the CEL vendor tree or the TabPFN v2 checkpoints.
The preflight must verify: `tabpfn-extensions` and `cel` import; `load_dataset("moons")` /
`load_dataset("heloc")` resolve; both v2 `.ckpt` files exist under
`experiments/zeroshot_cf/models/`; CUDA is visible with `TABPFN_DEVICE=cuda`; and
`uv run pytest experiments/zeroshot_cf/tests/test_context.py -q` passes. If it fails, fix
provisioning first — do **not** classify missing deps/vendor/checkpoints/CUDA as a
deferrable backlog item. Phase-A stages (1–3) are code/test only and do **not** need CUDA.

For each stage:

1. **Read the progress tracker** above and pick the stage to work on. If a stage is
   **IN_PROGRESS**, a previous run was interrupted mid-stage — resume and finish that one
   (re-read its steps, inspect the working tree to see what's already done) before
   starting anything new. Otherwise, take the first **PENDING** stage.
2. **Read the stage file** -- follow the link in the tracker to the stage's .md file.
3. **Read resources** -- if the stage references shared resources, find them in `resources/`.
4. **Resolve ambiguity yourself** -- there is no user to ask during an autonomous run.
   Pick the most reasonable interpretation that fits the codebase and existing
   conventions, record it under **Decisions**, and proceed. Only defer to the Backlog
   if the ambiguity genuinely blocks any sensible implementation.
5. **Implement** -- execute the steps described in the stage.
6. **Validate** -- run the verification checks and the test suite. **If anything fails,
   do not stop — triage it via the self-healing loop below.**
7. **Update this index** -- mark the stage DONE in the progress tracker, add brief notes
   about what was done and any deviations. Log every problem you hit in **Fixed Issues**
   (if resolved) or **Backlog** (if deferred). Never silently drop a problem.
8. **Commit** -- create an atomic commit with the message specified in the stage.
   Include all changed files (code, config, docs, and this plan's index.md).

Repeat until every stage is DONE or terminally deferred. After the last stage, **sweep
the Backlog**: attempt any items that are now resolvable, and leave the rest for a
follow-up run.

### Self-healing loop (handling problems)

When a step fails — failing test, build/lint/type error, a bug in the new code, an
unexpected runtime error:

1. **Triage** the problem as *light* or *heavy*.
   - **Light** -- self-contained and fixable in a focused effort: a failing unit test,
     a lint/type error, a missing import, a small logic bug in code you just wrote.
   - **Heavy** -- needs an architectural decision, spans many files, depends on an
     external blocker, contradicts the plan's assumptions, or has already survived a
     fix attempt.
2. **Light → delegate the fix to a subagent.** Spawn a focused subagent (Agent/Task
   tool) with: the failing command and its full output, the relevant file paths, the
   stage goal, and a crisp deliverable (e.g. "make `<test>` pass without weakening
   assertions"). Delegating keeps the main execution context clean. Re-run verification
   when it returns. Cap at **2 attempts per issue** — if still failing, treat it as heavy.
3. **Heavy → defer to the Backlog.** Add a self-contained entry (see the Backlog table).
   Do **not** keep grinding and do **not** halt the plan.
4. **Decide the stage's disposition:**
   - If the stage's core goal is met without the deferred item → mark **DONE**, note the
     backlog reference, and continue.
   - If the deferred item is essential to this stage → mark **BLOCKED**, note the backlog
     reference, and continue to the next *independent* stage. Only stop the run when every
     remaining stage depends on blocked work.
5. **Record** the outcome: resolved problems → **Fixed Issues**; deferred problems → **Backlog**.

### Guardrails

- Keep every commit in a working, buildable state.
- **Never weaken, skip, or delete a test to make it pass.** If a test is genuinely wrong,
  fix it correctly and note it in Fixed Issues.
- Never use `git commit --no-verify`.
- Don't expand a stage's scope to chase a heavy problem — that's what the Backlog is for.
- **Offline guarantee**: every run must work with no network. Models load **only** via
  `from checkpoints import get_models`; never import `tabpfn_client` or call the cloud API.
- **Do not modify `src/tabpfn/**`** — zero architecture changes.
- **Never fabricate a metric.** If a full-scale run is deferred or bounded, log the exact
  effective `n` and mark it; do not copy or interpolate rows into a results CSV.

## Decisions

Decisions made during planning (2026-07-07):

1. **Scale = statistically-stable bounded, not the entire split** (user decision). HELOC
   full-scale runs use `--max-test 200`; MOONS uses its full test split (~200 rows, cheap).
   The entire 2092-row HELOC split for the 16-cell kNN grid would take weeks of DGX
   wall-clock (Exp6 at n=15 already ≈5.3 h); n≈200 shrinks the ±0.12 validity noise to a
   publishable CI at ~3 DGX-days. Log the effective n per run.
2. **Re-run all four experiments** (Exp5, Exp6, Exp7, Exp9) at the chosen scale (user
   decision), not just the recommended cells — the selector and context *trends* (not only
   the winning cell) are what the ±0.12 noise currently obscures.
3. **Exp9 tractability = candidate caching + beam cap** (user decision), a reusable greedy
   speedup, not a one-off long detached job. Memoize per-candidate impute/score within a
   step and expose an optional `--beam K` candidate cap. Default (no beam) stays exhaustive
   and byte-identical; the cache is transparent. This resolves predecessor Backlog #4 and
   accelerates every greedy run.
4. **Heavy experiments run on the remote DGX `gx10-bdc5`** (predecessor Decision #12; memory
   `dgx-remote-experiments`): clone the branch, provision the env + v2 checkpoints, run
   detached via `nohup` + a `*.DONE` sentinel, pull results back and commit. Phase-A stages
   are local/CPU.
5. **The P1 fix precedes the Exp7 re-run.** Stage 1 corrects the shortcut predicate and
   Stage 6 regenerates *both* Exp7 CSVs from that single corrected code state, closing the
   P2 reproducibility gap in the same motion. Do not regenerate Exp7 CSVs before Stage 1 lands.
6. **Predecessor plan edits are limited to doc corrections.** Stages 2/8 touch
   `docs/plans/iterative-greedy-cf/index.md` only to fix the wrong Stage-1 SHA, backfill
   "(see git log)" rows from `git log`, and flip Backlog #4 → RESOLVED. No predecessor code
   or results are rewritten by this plan except via the full-scale re-runs above.
